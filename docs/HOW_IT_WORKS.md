# How VeriBook works: notes to explain it from

Each section: what it does, how, why it was built that way, how it fails, what is still weak. Code locations are given so any claim can be checked. File paths are relative to the repo root.

## 0. The map

```
document / API  →  extract  →  validate  →  match  →  investigate (AI)  →  verify (AI, only on escalations)  →  policy  →  audit (post + pay)
                                                                                                                     ↑
                              every step writes ONE decision row, chained to the previous one with SHA-256         |
                              a person's approve / reject / challenge is written into the same chain  ←  human review
```

Rule of the whole design: **deterministic code decides the money; AI advises, and can only make an outcome stricter.**

## 1. Reading an invoice (`lib/agent/extractor.ts`)

- **Order of attempts.** (1) A deterministic template parser reads labelled fields, line items in three layouts (block, inline, and a `Description / Qty / Unit Price / Amount` table, `lib/line-rows.ts`), and amounts. If it finds every required field *and the arithmetic reconciles*, that is the answer; no AI call. (2) Otherwise an LLM reads the document through a single forced tool call. (3) If the LLM is unavailable, the partial template result comes back at low confidence with the reason attached.
- **Confidence is computed, not asked for.** `assessExtraction` runs checks: vendor, invoice number, date, line items, total present; lines sum to the subtotal; subtotal + tax equals the total. Score = checks passed / checks run, capped at 0.95 (template) or 0.90 (LLM). A model's own confidence can only lower it. Below 0.85 the pipeline raises EXC-LAYOUT and a person looks.
- **Table rows are verified, not guessed.** A row is read only when its amount equals quantity x unit price to the cent; a row that does not reconcile is left out, the lines then fail to sum to the subtotal, and the document goes to the AI or a person. Colon-less totals (`Subtotal 2,140.00`, `Tax (8%) 171.20`, several CGST/SGST lines added up) are read only after a table header has been seen.
- **PDFs.** `lib/pdf-text.ts` takes the text layer with `pdf-parse` 2.x (a class; the route had been calling it as the old 1.x function, so every PDF upload failed until a test with a real PDF caught it). There is no OCR: a scan gets a 422 saying so.
- **Why.** A model's self-reported confidence is poorly calibrated; arithmetic that has to add up is an independent, cheap signal. It also means the common case costs no AI call.
- **Where it is weak.** The vendor name is the one field arithmetic can't verify. A `Vendor:` label is trusted; otherwise it is the first non-boilerplate, non-contact header line and is reported as `uncertain_fields`. The first benchmark missed that this heuristic was wrong on 44 of 125 ordinary invoices; see `docs/EVAL.md`.
- **If asked "why not just use an LLM for everything?"** Cost, latency, rate limits, and no way to tell when it is wrong. The checks give a defensible "send to a human" signal.

## 2. Intake (`lib/bills.ts`, `app/api/invoices*`)

Validated at the edge (400 malformed, 422 when the stated total isn't lines + tax, 409 if this vendor already sent this number), written in one transaction (vendor, bill, lines together), then the pipeline runs after the response via Next's `after()` so a serverless host doesn't freeze it half-way. The vendor is matched by name ignoring case and runs of spaces (`vendorKey`), not legal suffixes or punctuation: "Acme Ltd" and "Acme Inc" can be different legal entities, and merging payees is a fraud risk. An unknown vendor is created with trust tier `new`. The invoice's own tax and total are stored: an earlier version stored the sum of the lines and dropped tax, recording a $810 invoice as a $750 liability.

### 2b. Where the PO and the goods receipt come from (`lib/purchase-orders.ts`, `app/api/purchase-orders*`, the Orders screen)

Only the invoice arrives from outside. In a real AP system the PO is created by procurement and the receipt by the warehouse, and both reach AP by ERP sync. There is no ERP here, so they come from the seed script **or are entered on the Orders screen** (or read from a PO document into an editable draft, deterministic parser only; nothing is saved until the person presses Save). The invoice is linked to its PO by the PO number the document cites, within the same vendor; if there is none on file the invoice is treated as non-PO and says so.

- A PO number is unique: submitting it twice is a 409. A receipt is not naturally idempotent (the same delivery twice would double the goods received), so an identical receipt (same PO, date, receiver, condition, quantities) is refused with 409, and receipts for one PO are serialized with `SELECT ... FOR UPDATE`. Both are covered by concurrency tests that were mutation-checked.
- Only `accepted` receipts count as received; a `damaged` or `rejected` one is recorded but does not clear a line.
- Dates matter to the match: an invoice dated more than 7 days before the earliest receipt raises EXC-BEFORE_RCV.
- Not built: PO/receipt documents in free-form layouts (no AI reader for them), UOM on invoice lines, FX on POs (rate is 1.0), blanket POs from the screen.

## 3. Pre-match gates and the matching engine (`lib/matching/`, `lib/pipeline/match-stage.ts`)

- **Six gates before matching** (`pre-match-validation.ts`): readability (the 85% bar), duplicate, vendor status (flagged vendors blocked), currency, invoice date, mandatory fields. A failure stops the invoice deterministically; no AI is consulted.
- **Matching.** Invoice lines are matched to PO lines greedily by description similarity (trigram Jaccard ≥ 0.85); leftovers are paired one-to-one with the Hungarian algorithm (`line-match.ts`). Variances are classified with the spec's tolerance table (price ≤ 2% green, 2-5% yellow, > 5% red; quantity, line amount, grand total, tax, date gap likewise; `tolerance-zones.ts`).
- **15 exception codes** (missing PO, invoice before receipt, price/quantity variance, duplicate, non-PO, credit memo, partial, currency, tax, layout, bank-detail change, blanket ceiling, unit-of-measure, line not on the PO).
- **A line that is on no PO line** (an "Expedite fee", an item nobody ordered) raises `EXC-UNMATCHED_LINE`. It never auto-approves: up to $1,000 a reviewer decides, up to $10,000 a senior reviewer, above that it is blocked; the extra lines' amounts are added together. Before this existed, such a line was only counted, and an invoice whose every PO line matched could auto-approve with the extra charge in it. A line worth $0 is not flagged (nothing payable changes), and a line paired with a PO line as a likely unit-of-measure difference is reported as that, not twice. `decision-matrix.ts` turns findings into an action with a dollar-threshold table ("more restrictive wins") and a precedence order when several fire (bank-detail change outranks everything).
- **A line billed in a different unit** (single items against a PO in cases) needs a confirmed conversion on file ("1 case = 24 each", stored per vendor). Without one it raises `EXC-UOM_MISMATCH`. With one, the line is converted into the PO's unit and checked like any matched line: price, tax and quantity against what was received, counting earlier invoices against the same PO line in the same unit. Before, a conversion on file only cleared the exception and skipped every check, so 480 each against 10 cases of 24 (twice what was received) went through as clean. Known limit: the screen's three-way table still lists such a line as "not on the PO", and a blanket PO's quantity ceiling adds up invoice quantities without converting them.
- **Where the rules come from.** The written spec in `docs/ap-three-way-match-spec.md`. These are a defensible policy, not a given company's real thresholds; they are one table to change.
- **Not built:** goods-receipt accrual (GR/IR clearing). Bills post Dr Expense / Cr AP.

## 4. The two AI reviewers (`lib/agent/`)

- **Investigator** looks into an exception with tools (vendor history, PO and receipt lookup, duplicate check, learned corrections) and must finish by calling `submit_investigation`. **Verifier** reviews the Investigator's conclusion, only on escalations (`escalate_l2` / `block`), on a *different model family* (default `gpt-oss-120b` vs Qwen) so the second opinion is independent. If the Verifier disagrees, policy forces at least `escalate_l2`.
- **One tool loop** (`loop.ts`): every turn must call a tool (`tool_choice: required`), arguments are parsed strictly, the loop is capped at 8 turns, requests time out at 30 s.
- **Provider reality, all handled and tested with a fake client (`tests/agent-loop.test.ts`).** Models are retired without notice (the original id returned 404 on every call; the error now names the env var to change). Free tiers cap tokens per minute and per day (backoff, then a plain-language error). The model sometimes emits an invalid tool call, or answers in prose when a call is required, and the provider answers 400; that one 4xx is re-sampled up to three times because asking again is a different outcome. Confidence arrives on different scales (0.97, 97, 100) and is normalised to 0-1 at the boundary.
- **If asked "how do you stop the AI from approving something it shouldn't?"** It never decides. Policy takes the deterministic result and `moreRestrictive`-combines the AI's opinion with it (`lib/pipeline/orchestrator.ts` `computePolicyAction` / `tightenedByInvestigator`, used by both the pipeline and `lib/pipeline/reconsider.ts`). A regression test (`tests/reconsider-safety.test.ts`) pins this; removing the safeguard makes it fail, because an earlier version let a contested invoice's "auto_approve" cascade straight into posting and paying it.
- **The Investigator's recommendation is binding in one direction.** If the rules say auto-approve but the Investigator recommends anything stricter, the stricter outcome stands (reason code `INVESTIGATOR_HOLD`). It can never loosen a decision, and an AI "reject" is held for a person (block) rather than voiding the invoice on its own. Spelling noise a model really writes ("Escalate-L2", a non-breaking hyphen) is read; anything else is ignored. Before this, the recommendation was recorded and never applied on the normal path, so "escalate: a line isn't on the PO" at 0.95 confidence still ended in an automatic payment; and re-asking the Verifier could drop an Investigator's hold (a regression test now covers that case).

## 5. Policy and guardrails (`lib/pipeline/orchestrator.ts`, `lib/settings.ts`)

Policy = deterministic action, tightened by the Investigator's recommendation and by a disagreeing Verifier, then by two guardrails from Settings: a maximum auto-approval amount and a minimum Investigator confidence (default 90, because measured clean-match confidence is 0.93-0.98; a 95 default would hold a share of clean invoices). Both can only turn an auto-approval into a human review (reason code `POLICY_LIMIT`); neither can approve anything. Before this change the Settings page stored values that nothing read.

## 6. Posting and paying (`lib/ledger/journal.ts`, `lib/payments/payments.ts`)

- **Ledger.** Double-entry, balanced to the cent, idempotent (keyed on the source), serialised with a Postgres advisory lock, entry numbers taken from the highest existing number (not a count, which collides after any delete). A month's accounting period is opened on first use; a *closed* period still blocks posting; before, a single hard-coded period made every approval after 30 September fail. The invoice row is locked while posting (`FOR UPDATE`) so a concurrent reject can't slip in between the status check and the write.
- **Payment is simulated, and says so.** The earlier code called a payment host that doesn't exist in DNS, swallowed the failure with a `console.warn`, and recorded a mock payment as if money had moved. It is now an explicit simulation with a `SIMULATED-` reference, idempotent by construction (the payment id derives from the bill id, so a retry can't pay twice), and failure is separate from posting: a bill that posted but didn't pay stays "posted, payment failed" and shows up for a person.
- **Simplification to be honest about:** payment is initiated at approval, not scheduled by due date or early-payment terms; a real AP system would schedule.

## 7. The audit chain (`lib/ledger/decisions.ts`, `hash-chain.ts`)

- Every step writes one `decisions` row: who/what, inputs, claims, confidence, action, reason code. The row's hash is `SHA-256(previous hash | canonical JSON of the row)`; the whole chain is global, ordered by a sequence column, appended under an advisory lock.
- **What it proves:** after the fact, any change to or deletion of a past record breaks every later hash, and `GET /api/audit/verify` recomputes from the first record. **What it does not prove:** it is tamper-evident, not tamper-proof (someone with database write access could rewrite the whole chain consistently; anchoring the latest hash somewhere external is the next step), and it says nothing about whether a decision was *right*. It is not a blockchain, and nothing in the product says it is.
- One column is excluded from the hash on purpose: `superseded_by_id`, the single field that legitimately changes later (a reconsideration supersedes a decision). Everything else is immutable.
- The idempotency-key check is repeated *under* the chain lock; outside it, two concurrent writers with the same key could both pass the check and one would die on the unique constraint.
- **Checking one invoice** (`lib/ledger/trail.ts`, "Verify this trail" on the case page, `POST /api/invoices/:id/seal`): an invoice's records are interleaved with every other invoice's, so each of its records is checked three ways: its content against its hash, its stored `prev_hash` against the record just before it in the whole chain, and the record just after it against its hash. Recomputing a record only from its own stored `prev_hash` (what this check did until October 2026) passed a record that had been edited *and* re-hashed; the neighbour checks catch that, and a record removed or inserted next to it. Tampering far from this invoice is the whole-chain check's job.

### 7b. Audit support: auditor requests (`lib/pbc-shapes.ts`, `lib/audit/`, `app/api/pbc/`, the Audit screen)

- An auditor asks for evidence (a "PBC", provided-by-client, request): which invoices, and how each was approved. A request links real invoices (unknown ids are refused) and records who entered it. Only the `invoice_bundle` kind is accepted: the schema also names trial balances and AP aging, but nothing builds those, so a request for one could never be answered.
- **Evidence is derived, not stored:** for each linked invoice, its outcome (cleared, cleared by a person, not cleared, with the reason in words), the rules/AI/person behind each recorded step, and the hash of its latest record.
- **Closing hands the evidence over, on the record** (`lib/audit/pbc.ts`): one transaction, with the request row locked, writes an `audit_assemble` record ("provided as evidence for this request, closed by X") onto each linked invoice's trail and stamps who closed it and when. Closing twice changes nothing. These records are a person's act, so a reconsideration never supersedes them and they are not counted as pipeline stages.
- **Files** (`app/api/pbc/requests/[id]/files`): up to 5 MB each, base64 in Postgres (a production system would use object storage), recorded under the signed-in account, downloaded as an attachment with `nosniff` whatever type was uploaded.
- **Asking about a request** (`lib/audit/narrator.ts`) is the only AI here: the "ask why" explainer run per linked invoice, answering only from that invoice's records and citing them. Bounded: at most 10 invoices per question, 3 calls at a time; one invoice failing is reported on that invoice and the rest still answer.
- Roughly: the chain, the evidence and the request workflow are deterministic code; the AI only explains what is recorded and is never the source of a fact.

## 8. People are in the chain too (`lib/ledger/human-review.ts`, `lib/bill-workflow.ts`)

- **State rules in one place** (`bill-workflow.ts`, pure): which of approve / reject / challenge is allowed in which state, with the reason in words. The server enforces it and the API sends the same answer to the UI as `actions`, so a button is never offered that the server will refuse.
- **Atomic.** Approve = post to the ledger + write a `human_review` decision + a `reviews` row in one transaction; reject = status change + decision + row in one transaction. There is no moment where the ledger says "posted" but the chain has no record of who approved.
- **Races handled and tested** (`tests/human-review.test.ts`): approve vs reject on the same invoice (exactly one wins; a rejected invoice never reaches the ledger), a double-click (one decision, one entry, one payment), approving an invoice that is on hold (refused, nothing moves).
- **Challenge** records the reviewer's question in the chain first, then asks the Investigator/Verifier to reconsider with that question. A person's decision is never superseded by a machine's.

## 9. Vendor bank-detail change control (`lib/ledger/bank-change-review.ts`, `app/api/reviews/`)

The classic payment-fraud move is "our bank account changed". A recent change puts the vendor's invoices on hold. To release it: (1) a person phones the vendor on a number from their own records, not the change request, and logs the call; (2) *that person* records whether the vendor confirmed; (3) a *different* person signs off. A failed callback flags the vendor and the hold never lifts. Approving while the hold is on is refused by the server. Tested end to end through the real route handlers (`tests/bank-change-flow.test.ts`) and walked in the UI.
**Identity.** With sign-in on (section 9b), "a different person" compares signed-in accounts: the server takes the name from the session and ignores any name in the request. With sign-in off (local development only) it compares typed names. An earlier voice module recorded "confirmed" automatically on every call; that was removed because it made the control approve itself.

## 9b. Sign-in (`middleware.ts`, `lib/auth/`, `app/api/auth/`)

- **Accounts** come from `VERIBOOK_USERS`, a JSON list of `{username, name, passwordHash}`. Passwords are never configured in plain text: `npm run auth:hash -- '<password>'` prints a scrypt hash to paste. Names must be unique (case and spaces ignored), because they are what the trail records and what maker/checker compares. There is no self-sign-up and no roles yet: any account can approve.
- **Sessions** are stateless signed tokens (HMAC-SHA256 with `VERIBOOK_AUTH_SECRET`, 12 hours). The browser keeps the token and sends it as `Authorization: Bearer`, not as a cookie, so another site cannot make a browser send it, and the open CORS policy stays safe. Trade-off: a token cannot be revoked early; changing the secret signs everyone out.
- **The gate is the middleware**, in front of every `/api` route. A valid token becomes two request headers the routes trust (who is acting); the middleware deletes any copies a caller sends, so they cannot be forged. Without a token, a protected route answers 401. `/api/auth/login` and `/api/auth/session` are the only open paths.
- **Who is recorded.** `reviewerName()` (`lib/http.ts`) returns the signed-in account's name and ignores the body. If sign-in is on and a request somehow has no session, it refuses (401) rather than trusting the body.
- **Secure by default.** A production server (`NODE_ENV=production`) with no accounts configured answers every protected request with 503 and the reason, instead of running open; accounts without a long enough secret do the same. `VERIBOOK_AUTH=off` runs open on purpose, for a local demo. With nothing set in local development it stays open, as before.
- **Guessing is slowed:** 10 failed sign-ins per address per 15 minutes, then 429 (in memory, per server instance). A wrong password and an unknown user get the same answer, and an unknown user still costs one scrypt run, so timing does not reveal which usernames exist.
- **Tested** in `tests/auth.test.ts` (tokens: tampering, expiry, wrong secret; passwords; config; the middleware's 401/503/pass-through and header stripping; the login route including throttling; reviewer identity), and walked in the browser: wrong password, right password, return to the page you were heading for, decisions shown under the account, sign-out, protected pages after sign-out.
- **Not built:** roles (approver vs viewer), password change or reset, single sign-on, and audit of who changed Settings.

## 10. The screens (`frontend/src`)

An inbox, not a dashboard: tabs for what needs a person, what is processing, what is done, what was rejected; each row says in a few words *why*. The case panel answers, in order: what it is, why it is here, what you can do (and why a button is disabled), what the system checked, who decided what. "Why?" on any step asks the explain endpoint, which answers only from the recorded decisions and reports whether it cited any. Errors are shown with their real message; there are no silent fallbacks (the old client turned every failure, including a 409 "already approved", into an empty result).

### 10b. Asking about an invoice by voice (`frontend/src/lib/speech.ts`, `lib/useSpeech.js`, `components/case/AskVoice.jsx`)

The case page has an "Ask about this invoice" box. Type a question or press the microphone; the question goes to the **same explain endpoint** as the per-step "Why did it conclude this?" buttons, so the answer comes only from the invoice's recorded decisions and carries the same grounding note. The answer is shown and can be read aloud (answers to *spoken* questions are read automatically; for typed ones there is a Listen button, or a switch to read everything). Each step's "Explained" answer has a Listen button too.

- **How.** The browser's own speech recognition and speech synthesis. No server route, no model of ours, no new dependency. In Chrome and Edge the recording is sent to the browser vendor's speech service to become text; the screen says so. Firefox and most Safari have no recognition, so the microphone is hidden and typing works as before.
- **Read only.** Voice can ask and read; it cannot approve, reject, pay or change anything. A misheard word can give a wrong *answer*, and the question as understood is shown above it ("You asked (as heard)").
- **What is read aloud is not what is on screen.** The on-screen text has record ids, exception codes and field names. For speech these are turned into words: ids are dropped, `EXC-PRICE_VAR` becomes the screen's name for the code ("Price Variance"), `$17,710` becomes "17,710 dollars", dates and percentages are spoken, `unitPrice=$17,710` becomes "unit price is 17,710 dollars". No figure is dropped: unit tests cover each rule, and during development I read the spoken form of 24 live answers across all 12 demo invoices (that check script is not committed). If the answer cited no recorded decision, the same caution the screen shows is spoken too.
- **"Naturalise tone".** A button under the Ask box looks for a natural-sounding voice in the browser: an English voice whose name says Natural, Neural, Premium or Enhanced (Microsoft Edge's "... Online (Natural)" voices, Windows Natural voices, macOS Premium and Enhanced voices). If there is one it switches to it (Indian English first) and says a short sample; if not it says "Sorry, not available". Chrome's own Google voices and the older built-in Windows voices are deliberately not counted, so the button only says yes when the name does. The choice applies to the Ask box and to every step's Listen button, and is remembered as on or off only (the voice is looked up again on each page load, so a choice made on another computer cannot leave it pointing at a voice that is not there). If a chosen voice never makes a sound (an online voice with the network down, say), the same text is said once with the standard voice, the switch goes back to off and a message says so, so it never goes silent. Edge's natural voices are online voices: the answer text is sent to Microsoft to be spoken, and they need a connection.
- **Stuck states are handled in `speech.ts`** (a controller with the browser objects passed in, so every case is tested with fakes): a second press while listening is ignored; opening the microphone silences the speaker; a recording that ends with no words reports "no speech", and one that never ends is stopped after 12 s of silence or 30 s in all; a denied microphone, no microphone, or no network each have a message that says what to do; speech is read a sentence or two at a time (Chrome stalls on long text) with a watchdog per piece (Chrome sometimes never reports the end); Stop always resets the button; our own cancel is never shown as an error; leaving the page or switching invoice cancels both. If the question was spoken and the request fails, an apology is spoken and the real reason (for example the provider's daily quota) is on screen.
- **What was and wasn't verified.** Unit tests with fake recogniser and synthesiser: `tests/voice-speech.test.ts`; the id-matching fix below: `tests/explain-cited-ids.test.ts`. In the desktop app's browser: typed question, answer, real Windows voices (an Indian-English voice is chosen when installed), Stop mid-sentence, switching invoice mid-speech, a failed request, a phone-width layout, and the whole spoken-question path using a scripted stand-in for the microphone. **Not verified here: how a natural voice sounds, and any real natural voice** (this browser has none, and I cannot judge audio by ear: "Naturalise tone" was checked with its "not available" answer on the real voice list, and with one real voice renamed to look like Edge's "Natural" voice, which exercised the switch, the sample, the shared setting, the stale-setting reset and the fallback); and **real microphone recognition** (the development browser has no microphone, and it blocked the request; the app showed the "blocked" message). That needs a one-minute check in Chrome.
- **Two bugs found on the way, both in existing code.** A correct, cited answer was reported as "did not cite a recorded decision" when the model wrote the hyphens in a decision id as non-breaking hyphens (`explain.ts` now compares on plain hyphens). And when the explain request failed, the screen showed "500 Internal Server Error" instead of the reason, because the route put the message in a field the client does not read (it now also sends `error`).
- **Known limits.** Recognition quality is the browser's: Indian-English names and invoice numbers are the likeliest misses. The example questions were chosen because they answered well on the demo invoices; the explainer only knows what the decision records hold (it cannot say who approved something unless that is in a record). Not tested: iPhone/iPad Safari, which may refuse to speak the first answer unless it was started by a tap (the "Listen" button then works, and a refused start is reported after 5 s rather than staying silent). The answer text on screen still shows markdown asterisks from the model (existing behaviour of the narrative display).

## 11. How it is tested

- A separate schema (`veribook_test`), rebuilt each run, pinned with the connection's `search_path` (verified to hold on the pooled port); the live tables are never touched. A guard refuses to run the destructive migration against the default schema without `--yes`. This matters: the old suite deleted its own rows from the live hash chain, which its own comments flagged as a corruption risk.
- Properties, not just examples: races, idempotency, "AI text can't move money" (mutation-checked), the whole chain verifying after human actions, money round-tripping to the cent.
- Live-AI suites spend real quota and are skipped when no key is set or with `SKIP_LIVE_LLM=1`.
- Eval and benchmarks: `docs/EVAL.md`.

## 12. Money is exact

Money, quantities and rates were `REAL` (4-byte float). Rehearsing the migration on the demo data showed it directly: `SUM(total_amount)` over eight invoices returned **112460**; the true total is **112,460.50**. Columns are now `NUMERIC` (exact), read by the driver as JS numbers, and a test round-trips a $16,777,217.03 invoice and balances its ledger entry to the cent. `db/migrations/003_money_numeric.sql` converted the populated database. It was rehearsed on a copy first and **applied to the live database on 10 October 2026** after a full JSON backup. Before and after: row counts identical, largest amount (10,000.00) identical, the decision hash chain tip unchanged and the chain verifies, and 25 columns moved from REAL to NUMERIC (only the two model-confidence scores stay REAL). Float4 converts to numeric at 6 significant digits, so an amount above roughly $100,000 stored with cents could have lost them; the live data's largest amount is $10,000, so nothing was affected. Nothing is deployed anywhere: the app runs locally against this database.

## 13. What changed in the October 2026 refinement pass (so claims stay honest)

If an interviewer asks what was built when, this is the answer; do not describe these as part of the original build.

**Added on 10 October 2026:** PDF upload fixed (it was broken, see section 1); table-layout invoice rows; case-insensitive vendor matching; entering a PO and a goods receipt by hand or from a PO document, with the Orders screen; the "cited PO is not on file" warning after an invoice upload. Tests: `pdf-text`, `line-rows`, `extractor-table`, `purchase-orders` (real PDFs generated in the tests).

## 14. What I would do next

1. Roles (approver, viewer, administrator) on top of sign-in, single sign-on, and an audit record of Settings changes.
2. Schedule payments by due date and terms (and early-payment discounts) instead of paying at approval.
3. A real payment rail behind `triggerPayment`, calling the provider *before* writing anything and failing closed.
4. Add a currency-aware ledger (FX at posting).
5. Anchor the chain's latest hash outside the database.
6. A labelled corpus of real invoices to replace the synthetic eval, and a paid AI tier (or on-premise model) so quotas stop being a failure mode.
