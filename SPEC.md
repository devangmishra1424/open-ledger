## Agent architecture: tool-calling, not a hardcoded pipeline
The exception-classification/investigation step must be a genuine tool-calling LLM agent (using OpenAI function-calling with gpt-5-nano), not an if/else script — it should decide what evidence to gather and in what order, the way a real AP clerk investigates. Give it a small number of well-designed tools (per Anthropic's "writing tools for agents" guidance: clear namespacing, describe each tool like you're briefing a new hire, unambiguous parameter names, consolidate multi-step operations, return actionable errors not raw exceptions, keep the tool count small and high-impact):
- `get_po(po_id)` — returns PO line items/status, or an actionable message if not found ("no PO found matching this reference — check for a typo or treat as a non-PO invoice").
- `get_receipts(po_id)` — returns all goods receipts against a PO (handles partial/multiple receipts).
- `get_vendor_history(vendor_id)` — returns trust tier, bank_account_changed_at, and past invoice/correction history for this vendor.
- `check_duplicate(invoice)` — exact match plus embedding-similarity near-duplicate check against recent invoices.
- `recall_vendor_corrections(vendor_id)` — returns past human corrections/overrides recorded for this vendor (see memory/learning loop below) so the agent can apply previously-learned context (e.g. "this vendor always sends non-standard layouts, don't penalize confidence for that alone").
- `remember_correction(vendor_id, pattern, note)` — called when a human review overrides the agent's decision; writes a durable, vendor-scoped memory record that `recall_vendor_corrections` will surface on that vendor's future invoices. This is the genuine learning-over-time loop: show it working in the demo (first time a vendor's odd PO format is seen it escalates; after one correction, later invoices from that vendor recognize the pattern).
- `get_policy()` — returns the current tiered policy matrix (see below) as structured data, so the agent's own policy application is inspectable, not hidden.

Every tool call and its raw result becomes part of that invoice's decision record (see below) — this is what makes the swimlane and the "ask why" interface true rather than theatrical.

## Data model (implement as SQLite tables + TS types)
- `vendors`: id, name, bank_account_last4, bank_account_changed_at (nullable), trust_tier (trusted/new/flagged), created_at.
- `purchase_orders`: id, vendor_id, line_items (json: sku/description/qty/unit_price), status, created_at.
- `goods_receipts`: id, po_id, line_items (json: sku/qty_received/received_at), created_at. A PO can have multiple partial receipts.
- `invoices`: id, vendor_id, po_id (nullable — null means non-PO invoice), invoice_number, line_items (json), currency, tax_amount, total_amount, raw_source (text — either structured JSON or raw text/PDF-extracted text), received_at, status.
- `vendor_corrections`: id, vendor_id, pattern, note, source_invoice_id, created_at — the memory store behind `remember_correction`/`recall_vendor_corrections`.
- `decisions` (the core accountability record — see Accountability Layer section for full field list and rationale): id, invoice_id, node_id (extract/match/investigate/policy/audit), parent_decision_id, agent_id + model + model_version, started_at, ended_at, inputs_consumed (json: [{source, retrieved_at, content_hash, relied_on_span}]), tool_calls (json: [{name, args, raw_result, result_hash}]), claims (json: [{text, tag: grounded|ungrounded|contradicted, evidence_pointer}]), policy_evaluation (json: [{rule_id, threshold, actual_value, verdict}]), confidence, action_taken, reason_code (fixed enum — see list below, never a free-text "internal policy"-style string), forwarded_to, what_was_forwarded, prev_hash, hash (sha256 of prev_hash + canonical JSON of the rest of the row) — append-only, never updated or deleted.
- `reviews`: id, invoice_id, reviewer_name (picked from the fixed list, not a real account), action (approve/reject/request_info/contest), reason_code (enum), note (optional free text), created_at — a review is itself a new linked decision record, not a separate side table conceptually; store it so it chains into the same hash sequence.
- `reason_codes`: a small seed table of the fixed, versioned vocabulary (e.g. R01_QUANTITY_VARIANCE, R02_PRICE_VARIANCE, R03_MISSING_PO, R04_DUPLICATE_SUSPECTED, R05_VENDOR_BANK_CHANGE, ... one per exception type below, plus R00_CLEAN_MATCH) with a human-readable description — the UI and the agent both reference codes from this table, never invent inline strings.

## Exception taxonomy — implement detection logic for ALL 12, this is the core deliverable
1. Missing or invalid PO reference on the invoice.
2. Invoice received before the goods receipt is posted for that PO.
3. Price variance: invoice unit price vs PO unit price beyond tolerance (e.g. >2%).
4. Quantity variance: invoiced qty vs received qty beyond tolerance.
5. Partial shipment: invoice must match across multiple partial receipts against one PO.
6. Duplicate invoice: same vendor + invoice number + amount already seen, OR near-duplicate via embedding similarity on line items/vendor/amount/date.
7. Non-PO invoice (utilities/subscriptions) — different approval path, no 3-way match possible, route on amount/vendor-trust alone.
8. Credit memo netting: a credit memo must net against an open or future invoice from the same vendor, not be treated as a standalone bill.
9. Partial/short payment or disputed-then-partially-settled invoice.
10. Currency or tax-calculation mismatch.
11. Non-standard invoice layout / low-confidence extraction (the extraction step reports its own confidence; below a threshold, this fires regardless of what the content says) — UNLESS `recall_vendor_corrections` shows this vendor's layout was already learned as normal.
12. Vendor master-data fraud flag: vendor's bank_account_changed_at is within e.g. 14 days of this invoice — always escalate tier 2, never auto-approve regardless of amount/confidence.

Each invoice in the demo dataset should be engineered to trip exactly one of these (or be a clean match) so every type has a legible, isolated demo moment. Reserve one or two vendors specifically to demonstrate the learning loop (#11 corrected once, then recognized).

## Tiered policy (implement as an explicit, visible, editable policy object/table — not hidden if/else buried in code, and exposed via `get_policy()`)
- Tier 0 auto-approve: no exception types fired, confidence ≥ 0.9 from both models (OpenAI and TensorMux agree), amount < $2,500, vendor trust_tier = trusted. Auto-post to ledger, full decision+audit record still written.
- Tier 1 single-reviewer: amount $2,500–$25,000, OR vendor trust_tier = new, OR confidence 0.6–0.9, OR exactly one minor exception (variance within secondary tolerance, non-PO invoice). Goes to the reviewer queue.
- Tier 2 escalated: amount > $25,000, OR exception #6 (duplicate) or #12 (fraud flag) fired, OR the two models disagree on classification. Requires a documented rationale from the reviewer, cannot be single-approved, and the UI must show why it escalated.
- SLA: an item unresolved after a configurable window gets reassigned/flagged overdue (use a short window like 10 minutes of demo/real time so this is actually demonstrable live, and label it clearly as a demo-scaled SLA in the UI/README).

## Accountability layer: Decision Ledger + Constrained Narrator (this is now core, not stretch — it's the actual USP)
The point of this section: nothing in the pipeline should be a status pill. Every node should behave like a person who can justify their own action when asked.

**The record.** Every node writes its `decisions` row (schema above) at the moment it acts, never reconstructed after the fact. `reason_code` is always from the fixed `reason_codes` table — an agent or a human is never allowed to write a free-text justification as the primary reason, only as an optional supplementary note. This is what makes "why did you do that" answerable rather than hand-wavy.

**The "ask it why" interface — retrieval-only, never a general chatbot.** Every node in the swimlane and every row in the audit viewer gets a click-to-interrogate popover. When someone asks "why did you do that?" or "why this and not that other invoice?", the answer is generated in two hard-separated stages:
- Stage A (fuzzy, allowed to be approximate): semantic search over decision records (using the OpenAI embeddings) to find the small set of relevant `decision_id`s.
- Stage B (constrained, must be exact): fetch the complete, exact stored records for exactly those IDs plus their directly linked parent/child records, and give the answering call ONLY that closed set as context. Every claim in the answer must cite a specific `decision_id` + field. Verify each citation actually appears in that exact record before showing the answer (a simple string/entailment check is sufficient for the hackathon — this doesn't need to be research-grade). If a sub-claim can't be grounded, the answer must say "not recorded" for that part — never silently invent or infer across the gap.
- Answers should default to contrastive framing where possible ("held rather than auto-approved, because X; would have cleared if Y") — this is cheap since the policy engine already evaluates the alternative branch, and it's how humans actually ask "why" questions.

**Contest is a real, logged action, not a comment box.** Every reviewed/escalated item gets a "contest" control alongside approve/reject. Pressing it writes a new decision record linked to the original (not a free-floating complaint) and can trigger a bounded re-run of the investigation step with the contest reason as additional context.

**Three-tier drill-down**, on every single node, no exceptions: Level 1 = one-line status + reason code, always visible in the swimlane/queue. Level 2 (click) = the specific rule/evidence that fired, in the contrastive phrasing above. Level 3 (click again) = the full raw decision record — tool calls with real arguments/results, model + version, policy version, hash. Nothing should require reading code to understand; it should all be visible in the interface.
